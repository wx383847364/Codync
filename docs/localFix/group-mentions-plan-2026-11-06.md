## 0. 范围与不变量

解决四个问题：键盘选人、按稳定身份派工、忙时可靠排队、后续发言与重启不丢任务。

必须始终成立的不变量：

1. **一个房间同一时刻只有一个 runner 在推进调度。** 超时留下的在途执行不算第二个 runner。
2. **投递记录是唯一的派发依据。** actor 只承载执行，不自行挑选投递，也不持有"谁该说话"的判断；选哪一条由房间 runner 决定。
3. **投递终态只能被满足条件的一方写入。** 迟到结果、旧 attempt、旧代次都不能覆盖它。
4. **不承诺外部副作用恰好一次。** 数据库能保证"不丢记录、不重复领取"，不能保证"命令只执行一次"。
5. **房间对话顺序不变。** 默认一次一个人说，说完下一个才看上下文。

不做的：跨电脑群聊、成员主会话架构改造、并行扇出模式、通用工作流框架、新的消息服务。

## 1. 状态机与术语

### 投递状态

```text
queued → claimed → started → completed / noReply / failed
                         ↘ interrupted / cancelled
```

| 状态 | 含义 | 谁写入 |
|---|---|---|
| `queued` | 已持久化，等待调度 | 入队事务 |
| `claimed` | runner 已指定该投递，actor 条件领取成功，尚未允许发送 | actor，领取时写 |
| `started` | 已提交"可能已发送 prompt"，之后才真正发送 | actor，发送前单条提交 |
| `completed` | 有结果 | 完成事务 |
| `noReply` | `speak` 型的 `(pass)` | 完成事务 |
| `failed` | 启动失败或执行报错 | 完成事务 |
| `interrupted` | 重启或强制切换导致的中断 | 恢复逻辑 / 切换逻辑 |
| `cancelled` | Stop、移除成员、删除群 | 取消事务 |

三条容易写错的规则：

1. **超时不是终态。** 超时只释放房间的等待位置，允许下一个成员执行；原投递仍是 `started`，等迟到结果。迟到结果通过条件更新完成它；如果它已经 `cancelled`/`interrupted`，只保存迟到记录。
2. **`deferred` 不是状态。** 它是 runner 本轮的跳过标记，投递保持 `queued`，身份、正文、`room_seq` 都不变。不要新增 `deferred` 状态值。
3. **`started` 是保守边界。** 它覆盖"提交后还没发送就崩溃"，这类请求也由用户确认后重试。

### 投递类型

| 类型 | 来源 | 允许 `(pass)` | 完成语义 |
|---|---|---|---|
| `speak` | 用户消息的 @ / 成员回复里的 @ | 是 | `(pass)` → `noReply`，房间不显示 |
| `task` | 群内 `message_bot` | 否 | `(pass)` → `noReply` 且卡片标"未提供结果" |

`speak` 的请求正文来自**来源 entry**，不从窗口重建：执行时按 `source_entry_id` 读出完整原文、附件与引用，24 行窗口只作补充上下文。`task` 的正文是工具入参，执行时必须保留，房间上下文附在后面。两者的原文都不允许被历史窗口截掉。

### runner 与 execution

- **runner**：每房间一个，推进队列的调度者，取代现有 `run()` 的循环。
- **execution**：成员 agent 的一次 turn。超时后 runner 走了，execution 还在跑——这不算第二个 runner。

## 2. 输入与身份

### 2.1 候选列表

- 输入框上方纵向列表，复用命令菜单的样式、动画与键盘约定。
- `↑/↓` 循环、`Enter/Tab` 插入、`Esc` 关闭；选择不发送消息。
- 光标保持在输入框；鼠标悬停与键盘高亮同步；选中项滚入可见区域。
- 按**光标所在**的 `@` 片段过滤，只替换该片段，前后文字保留。
- IME 组合期间不拦截确认键；`Shift+Enter` 仍是换行。
- 同名成员在候选行显示简短辅助信息（ID 前缀或分组），仅用于区分。

### 2.2 消息身份

`send` 增加可选字段：

```text
mentions: [{ botId, start, end }]
```

- `start`/`end` 是**实际请求正文**的 UTF-16 半开区间。
- 客户端在编辑时维护区间：片段被修改或删除后取消绑定；绑定不因成员改名失效。
- 携带 `mentions` 时正文原样发送。host 先在原正文上校验，再执行既有 `trim()`，并同步换算区间后保存。客户端**不得**先裁剪正文却沿用旧区间。
- host 校验：整数边界、代理对边界（不得切在 UTF-16 代理对中间）、区间不重叠、区间内以 `@` 开头、目标属于当前群。
- 校验失败 → 拒绝发送，客户端提示重选并保留草稿与绑定。

四端的持久化要求：草稿、离线队列、发送重试、乐观消息、历史追赶都必须带上 `mentions`。桌面 `bot-store.ts` 的 `send()` / `retry()` 都走同一份数据，不要把绑定只放在组件状态里。

## 3. 路由

### 3.1 结构化片段

1. 结构化片段按 `botId` 路由，片段内部的名字不参与解析。
2. 片段之外的正文才做文本解析。
3. 已保存的历史不重新解析；旧客户端的新消息在入库时解析并固定结果（把解析出的目标写进 entry data）。

### 3.2 文本解析

**新增一个保留字节偏移的屏蔽扫描器**，不新增依赖，也不复用 `host/src/tui/md.rs`（它是显示层，会丢弃围栏标记并按终端宽度重排，偏移已失效）。

扫描器输出"不可路由区间"，只在未屏蔽区间匹配 `@`。必须覆盖：

- 围栏代码块：``` 与 ~~~，含 info string，允许更长围栏包住更短的
- 行内代码：1..N 个反引号，成对匹配
- 缩进代码块：行首 4 空格或制表符
- 引用行：`>` 开头（含嵌套 `>>`）
- autolink 与裸 URL（`http://`、`https://`、`www.`）
- 邮箱：`local@domain.tld`
- 章节标记 `@all` / `@everyone` 视为指派表达，不屏蔽

`@` 出现在上述区间内 → 当普通文本，不派工。

### 3.3 优先级与失败

1. 精确完整名称优先。
2. 去空格名称、首词简称只接受唯一匹配。
3. `显式选择 ∪ 有效手打目标 ∪ 引用回复目标`；有效 `@all`/`@everyone` 扩展为当前成员全集。
4. **无匹配**的 `@word` → 当普通文本，不失败（`@here`、`@某人` 不是成员时不该阻断发送）。
5. **多重匹配** → 拒绝发送，提示重选，不部分派发、不退化为全员。
6. **结构化绑定失效**（正文已改到对不上）→ 拒绝发送，提示重选。
7. 没有任何指派表达 → 全员响应（保持现状）。
8. 引用正文不触发额外派工。

## 4. 群内工具派工

沿用 `message_bot(botId, message)`，新增群内分支：

- 来源成员、群、执行 ID 取自 host 的执行上下文，**不接受模型传入 lane**。
- 群内分支直接创建 `task` 投递，不走 `BotRequest`/`BotReply`（那条路会把回复送进发送者私聊）。
- 目标必须是当前群成员。资格校验统一为"群成员资格"，不再用 `visible_bot` 的可见性判断，避免隐藏成员在文字与工具两条路径上行为不一致。
- 工具立即返回 `{ requestId, status: "queued" }`，发送者继续当前任务。
- 接收者在其现有会话、来源群 lane 执行；最终回复以接收者身份写入群，并关联 `deliveryId`。

工具签名增加可选的幂等键：

```text
message_bot(
  botId: string,
  message: string,
  idempotencyKey?: string   // 同一任务重传时复用；不要为新任务复用
)
```

- 作用域是 `(来源成员, 来源群, 目标, key)`：不同成员、不同群、不同目标即使键相同也互不影响。
- 同键且正文完全相同 → 返回原投递的 `requestId` 与当前状态，不新建。
- 同键但正文不同 → 返回冲突错误（"幂等键已用于另一个任务"），**不能返回另一项任务的结果**。判断依据是正文逐字相等，不是相似度。
- 没有键 → 不做去重，也不猜测。

去重与展示：

- 同一次执行已向某目标成功创建 `task` 投递时，最终回复里对该目标的 `@` 只作为发言记录，不再创建投递。第二份任务必须再调一次工具。
- 不按正文相似度合并，不跨执行合并。

## 5. 持久投递

### 5.1 表

`deliveries`（SQLite，与现有库同文件）：

| 列 | 说明 |
|---|---|
| `id` | 投递 ID（uuid） |
| `room_id` | 群 ID |
| `kind` | `speak` / `task` |
| `source_kind` | `user` / `reply` / `tool` |
| `source_entry_id` | 来源 entry（`user` / `reply`） |
| `source_execution_id` | 来源执行 ID（`reply` / `tool`） |
| `source_bot_id` | 发起成员（`reply` / `tool`） |
| `target_bot_id` | 目标成员 |
| `body` | 原始任务正文，逐字保存（`task` 必填；`speak` 不重复存，执行时按 `source_entry_id` 读取）。幂等键的同键比对用它 |
| `room_seq` | 房间内单调序号，入队时分配，**runner 按它排序** |
| `batch_root_id` | 批次根：发起链的用户消息 entry。`speak` 从用户消息出发时等于 `source_entry_id`，成员引用时继承；私聊发起的 `task` 为空 |
| `attempt` | 重试代次，从 1 开始 |
| `parent_id` | 被重试的原投递 |
| `round` | **对话轮次**：用户消息 = 1；成员发言 = 产生它的那次执行的轮次 + 1；`task` 继承发起者的轮次，自己不推进 |
| `chain_depth` | **链深**：任何一次派工的跳数，文字与工具统一计数，从来源投递 +1，跨类型不重置 |
| `idempotency_key` | 调用方提供，可空 |
| `status` | 见状态机 |
| `claimed_at` / `started_at` / `finished_at` | 时间戳 |
| `last_error` | 失败原因 |

索引与约束：

- `UNIQUE (source_entry_id, target_bot_id, kind, attempt) WHERE source_kind IN ('user','reply')`：同一来源对同一目标、同一代次只产生一条。**`attempt` 必须在键里**，否则用户重试会撞约束。
- `UNIQUE (target_bot_id, idempotency_key) WHERE idempotency_key IS NOT NULL`：**作用域不够，改为** `UNIQUE (source_bot_id, room_id, target_bot_id, idempotency_key) WHERE idempotency_key IS NOT NULL`。不带 `attempt`：同键重传返回原投递（不新建行）。
- 用户主动重试：新行 `attempt = 原 + 1`，`parent_id` 指向原投递，**`idempotency_key` 置空**（调用方并未参与重试）。原始请求的重传与用户重试是两件事，不能共用键。
- 同键不同正文在插入时比对 `body`：相等才复用原行，不等则报冲突，不写库。
- `INDEX (room_id, status, room_seq)`：runner 选下一条。
- `INDEX (batch_root_id, kind, status)`：预算计数。
- `INDEX (status, room_id)`：周期补查扫"有排队投递的房间"。
- 不设 `(source, target)` 的全局唯一：同执行两次工具派工必须都保留。

### 5.2 事务

| 场景 | 同一事务内 |
|---|---|
| 用户消息 | entry 插入 + N 条投递（`speak`） |
| 成员最终回复 | 回复 entry 的 `final` 更新 + 该回复产生的投递（`speak`） |
| 工具派工 | 幂等查询 + 容量检查 + 投递插入（`task`），提交后才返回成功；投递行的 `id` 就是这次调用的记录，不另建表 |
| 完成 | 回复/结果 entry + 投递终态（带条件） |

事件在事务提交后发布，沿用现有 entry/event 通道，不另建消息服务。

**写入顺序（顺序即断言，三条都要有测试）：**

1. **幂等查询先于容量拒绝。** 已接受请求的重传，即使当前容量已满，也返回原投递；不能因为"现在满了"把一个已经受理的请求报成失败。
2. **容量检查与插入在同一事务内完成。** 先查数量、再另开事务插入，两个房间并发派工就能突破 64/16。用 `BEGIN IMMEDIATE`（rusqlite：`transaction_with_behavior(Immediate)`，默认的 `DEFERRED` 不够），计数与插入在同一个事务里。
3. **预算检查与 `claimed` 预占在同一条条件更新里完成。** runner 的下发前检查只是预检，actor 领取时必须再判一次（见 §5.3）；两条路径必须用同一个计数谓词，否则预检和领取会各算一套。

两个计数谓词不同，不要合并：

| 计数器 | 谓词 | 为什么 |
|---|---|---|
| 发言预算 | `speak` 且状态 ∈ (`claimed`,`started`,`completed`) | `queued` 不计，否则 12 个 @ 在创建时就砍掉 2 个 |
| 派工容量 | `task` 且状态 ∈ (`queued`,`claimed`,`started`) | 沿用现有"未完成请求"语义，`queued` 也要占，否则可以无限堆积 |

并发重传的处理：插入撞上幂等唯一约束时，**回读原行并返回它**，不要把约束冲突当成错误抛给调用方。否则第 1 条只在"没有并发"时成立。

### 5.3 领取

领取分两步，**actor 不自行挑投递**：

```text
-- 1. runner 从队首开始取；本轮已 deferred 的（在内存里）跳过后再取下一条
SELECT id, target_bot_id FROM deliveries
 WHERE room_id = ? AND status = 'queued'
 ORDER BY room_seq LIMIT 1;

-- 2. actor 只条件领取被指定的那一条；speak 同时判定预算（与 §5.2/§6.4 同一谓词）
UPDATE deliveries SET status='claimed', claimed_at=?
 WHERE id = ? AND target_bot_id = ? AND status='queued'
   AND ( kind <> 'speak'
         OR (SELECT COUNT(*) FROM deliveries d
              WHERE d.batch_root_id = deliveries.batch_root_id
                AND d.kind = 'speak'
                AND d.status IN ('claimed','started','completed')) < 10 )
RETURNING id, kind, source_kind, source_entry_id, source_bot_id,
          body, batch_root_id, round, chain_depth, attempt;
```

- `id` 是 UUID，`ORDER BY id` 没有入队含义。顺序一律用 `room_seq`。
- actor 若自行领取任意 `queued`，会抢走 runner 还没轮到的投递，房间顺序立刻失效。**actor 只能领 runner 指定的 id。**
- 条件更新同时兜住四种竞争：已被取消、已被别的 runner 领走、目标不匹配、预算已满。返回 0 行时必须区分原因：状态已变 → 跳过；预算已满 → 取消该批次剩余 `queued`，不要当成"这条有问题"继续重试。
- 领取处的预算判定不是重复劳动：runner 的预检发生在下发前，actor 的领取可能晚于另一个领取或一次重试；只有落到同一条 `UPDATE` 的 `WHERE` 里才是真的原子。
- 本轮已标 `deferred` 的 id 记在 runner 内存里，同一次推进不再选它，否则会在队首空转；下一次 `ensure_runner` 或周期扫描才重新考虑。
- 启动、提交后通知、周期补查都触发**房间调度**（`ensure_runner`），不触发逐 bot 抢领。
- `claimed` 在 actor 真正取到时写，不在入库时写；否则成员在别处忙一小时，卡片会显示"执行中"一小时。
- 会话准备完成后提交 `started`，提交失败则不得发送 prompt。

### 5.4 恢复

顺序固定：

1. `hub.start()` 里先跑 `expire_pending`。
2. **`expire_pending` 的 SQL 增加排除条件**：`AND json_extract(data,'$.deliveryId') IS NULL`。不采用"两种可选实现"，就这一种。
3. 投递恢复（单个事务）：`queued`/`claimed` → 保持或回到 `queued`；`started` → `interrupted`，原因写"host 重启时正在执行，结果不确定"。
4. 恢复结果更新对应卡片（此时卡片尚未被 `expire_pending` 动过）。
5. 再 `spawn_bot`，最后为有排队投递的房间 `ensure_runner`。

**恢复不得自动重放 `started`。** `claimed` 可以重新排队：该状态的定义就是"尚未允许发送"。

## 6. 房间调度

### 6.1 单 runner

- `start()` 改为 `ensure_runner(room)`：已有 runner 时只标记"队列有变化"，不再 spawn。
- runner 每推进一步重读队列；退出时在 `Rooms` 锁内清 `running` 并再查一次队列，仍有可执行项就继续。
- 启动时为有排队投递的房间 `ensure_runner`。
- 现有 epoch 降级为 runner 的代次：只用于让旧 runner 退出，不再决定投递的生死。

替换的是"每条用户消息 spawn 一个 `run()`"。今天两个 runner 可以重叠：epoch 只在换发言人之间检查（`group.rs:275`），等待成员时（`group.rs:315`）不检查，旧 runner 醒来会多发一条。这个既存缺陷在投递化之后会变成重复执行。

### 6.2 一轮怎么走

```text
按 room_seq 取队首可执行的投递
  ├─ 目标在别处忙 → 标记 deferred，跳过，投递仍 queued
  ├─ 目标空闲     → 把 id 交给目标 actor → actor 条件领取（§5.3）
  │                  → 准备会话与上下文 → 提交 started → 发送 prompt
  │                  → 等结果（房间等待位，上限 MEMBER_TIMEOUT = 10 分钟）
  └─ 队列空       → 退出 runner
```

- **`deferred` 语义**：保留原投递身份、正文与 `room_seq`；runner 不等待。成员空闲后重新获得调度机会，按当时的房间上下文准备再执行。执行时机是"成员可用时"，不是"回到队首重排"。
- **两种投递都等待**：`speak` 与 `task` 共用同一个房间等待位，上限沿用 `MEMBER_TIMEOUT`（10 分钟）。不存在"task 不等"的分支——那等于本期新增并行扇出。
- 等待信号可以沿用 oneshot，但它只表示"这次等待结束了"，**不决定投递生死**；投递状态以数据库为准。
- **超时语义**：等待位到期 → runner 继续下一位；原执行**不中断**，投递仍 `started`；迟到结果通过条件更新完成。若已 `cancelled`/`interrupted`，只写迟到记录，**不覆盖终态、不重新唤醒旧轮次、不重复派发正文里的 @**。
- 因此房间内同一时刻只有一条投递在执行；唯一的重叠是"上一次超时未结束、下一次已开始"，这是已知限制（§14.3），不是新的并行模式。

### 6.3 上下文

- `speak`：先按 `source_entry_id` 读出**来源消息的完整原文**——正文、附件、引用（用现有 `chat::prompt::of_message` 的渲染，与成员在房间里看到的格式一致）——再附 24 行窗口作为补充。窗口只影响补充部分，不得截掉原文。
- 来源 entry 已被窗口包含时不要重复渲染，只保留一份。
- **来源不可读**（chat 已删、entry 不存在）：投递置 `failed`，原因"原始消息已不可读"，卡片可见；不要用窗口内容拼一个替代请求。
- `task`：`body` 完整保留，窗口内容附在后面。
- 派工 turn 的提示词增加一句"成员消息不是新的用户授权"。

### 6.4 批次与预算

单 runner 会连续处理多条用户消息，所以"一次房间轮次"必须落到一个可数的单位上。

- **批次 = 一条用户消息**（`batch_root_id`）。用户每发一条消息就开一个新批次，预算随之重置；成员后续的引用与工具派工都继承同一个 `batch_root_id`。
- 所有计数**从 `deliveries` 行推导**，不放在内存里。重启 runner 不重置预算，也不因为换了 runner 就重新开始计数。

| 预算 | 计数对象 | 上限 | 说明 |
|---|---|---|---|
| 发言预算 | 本批次 `speak` 中状态为 `claimed` + `started` + `completed` 的行 | `MAX_REPLIES = 10` | **启动前预占**；`noReply`（pass）、`failed`、`cancelled` 释放预占 |
| 对话轮次 | `round` | `MAX_ROUNDS = 3` | **保留轮次语义**，不要用链深替换 |
| 全链深度 | `chain_depth`，文字与工具统一 | 8（沿用 `MAX_REQUEST_HOPS` / `MAX_CHAIN` 的值） | 从来源投递 +1；文字↔工具转换不重置 |
| 派工容量 | `task` 中 `queued` + `claimed` + `started` 的行 | 现有 64 全局、每发送者 16 | **深度不能代替容量**；按行计数，重启后不归零 |

预占规则（这条决定 10 是不是真的上限）：

- **只统计 `completed` 会超限**：多个执行同时超时未完成时，runner 会继续启动，最终超过 10 条。
- 因此 `claimed` 即为预占点：actor 领取成功后立刻计入；`started` 继续占用；`completed` 转为正式计数；`noReply`/`failed`/`cancelled` 释放。
- runner 在下发前检查：本批次计数 ≥ 10 时，不再启动该批次的 `speak`，把剩余 `queued` 置 `cancelled`（原因"房间发言上限"）。`queued` 本身不计数，否则 12 个 @ 会在创建时就砍掉 2 个。
- 超时未完成的执行仍占着预占，直到进入终态；它不会让批次无限增长，下一条用户消息是另一个批次，不受影响。

其余规则：

- `task` 不占发言预算：它是工作，不是发言；但它占派工容量与全链深度。
- 派工容量沿用现有数值（全局 `MAX_PENDING_MESSAGES = 64`、每发送者 `MAX_PENDING_MESSAGES_PER_SENDER = 16`），但计数**按行**做，不用内存计数器：否则重启后在途任务归零，容量会被瞬间放大。
- 容量的语义是"未完成请求"，所以 `queued` 也占额度——现有 `reserve_message` 正是入队即占用、完成才释放。如果只算 `claimed`/`started`，发送者可以无限堆积排队任务，上限形同虚设。
- 迟到执行仍属于原批次，完成时计入；若此时预算已满，它自己的 @ 不再产生新投递。
- 已 `started` 的执行照常完成，但不能再派生新投递。触限的剩余投递按行显示在卡片上，不静默丢弃。
- 迟到回复因预算被压制时，房间要留一条可见说明，不能让用户以为 @ 生效了。

**轮次与深度不能互相替代。** 轮次是对话推进（一条用户消息 → 成员发言 → 被点名的人再发言），深度是派工跳数（文字与工具都算）。一次 `task` 派工会增加深度但不推进轮次；把 `MAX_ROUNDS` 换成链深，等于让工具调用吃掉对话轮次，是行为变更，不是注释调整。本方案不采用。

`MAX_CHAIN = 8` 作为独立常量随 `sweep` 删除而退役，但**全链保护必须保留**：由 `chain_depth` 统一承担，文字与工具互相转换时从来源投递的行值 +1，不得回落到内存里的默认 0。

## 7. 生命周期

### 7.1 Stop

- 群 Stop：先把该群未完成投递写 `cancelled`，再通知成员取消该群当前执行。不依赖内存里有没有 epoch。
- 私聊 Stop：保留其他群的排队投递，只停当前会话的 turn。

### 7.2 移除成员 / 删除群

- runner 选中、actor 领取、发送前各校验一次目标资格（三处都查，防止"创建时还在群里"）。
- 移除成员：取消该成员在该群的未完成投递；成员已排队的 turn 也要能被打断。
- 删除群：级联取消该群全部未完成投递，卡片标原因。
- runner 选中时若目标已不是成员：该投递置 `cancelled`（原因"已不在群内"），runner 继续下一条，不重试。

### 7.3 `/new`

三个选项，默认第一个：

1. **在当前任务结束后新建会话**（默认）。显示"将在当前任务结束后新建会话"，提供"取消切换"。
2. **立即停止并新建**。先取消当前执行，等待取消确认。
3. **取消切换**。清除待切换标记。

没有在途执行时，前两个选项都立即应用；不要留一个只等在途 turn 的标记。

强制切换流程（顺序即实现顺序，`forget_session()` 在持久化之后）：

1. 设 `pending_new_session`，调用 `cancel_turn()`；等待 `turn_ended`。
2. 超过现有取消宽限期（`CANCEL_GRACE = 15s`，`agent/bot/mod.rs:479`）→ 走现有机制终止旧 agent（`mod.rs:409-412` 已实现），等 `turn_ended`。
3. **`turn_ended` 后先落盘**：当前投递置 `interrupted`，原因"因强制新建会话而中断"；若这轮还有结果，结果 entry 与状态同一事务提交。其他排队投递保留。
4. 落盘失败 → 进入存储故障状态（§10.1 的 DB 无关事件），**不 `forget_session()`、不新建会话**，等手动重试保存。
5. 落盘成功 → `forget_session()` + 记忆 flush。
6. runner 继续推进；保留的排队投递在新会话里执行。

第 3 步必须在第 5 步之前。先切会话再补状态，会在落盘失败时留下"会话已换、旧投递状态不明"的组合。

注意：成员的主会话与它的群共享，`/new` 会同时重置群上下文。UI 文案要说清楚，这不是新行为，但用户不知道。

## 8. 幂等

三件事分开，不要合并成一个"键"：

| 用途 | 键 | 谁生成 | 承诺 |
|---|---|---|---|
| 追踪 | `execution_id`（每次 turn） | host | 无 |
| 追踪 | 投递行的 `id`（工具派工一次一条） | host | 无 |
| 去重 | `idempotency_key` | 调用方，可选，需复用 | 仅在提供时，按 `(来源成员, 来源群, 目标, key)` 去重 |

- 键的作用域必须带来源成员与来源群：同一个键被两个成员、两个群分别使用，是两件事。
- 同键且 `body` 逐字相同 → 返回原投递；同键但正文不同 → 冲突错误，不返回另一项任务的结果，也不覆盖原行。
- 没有幂等键 → 不承诺跨连接去重，也不按正文猜测。
- MCP 连接内可用 `(连接, jsonrpc id)` 做进程内去重，属优化，不进验收。
- 用户发送的重试继续用现有 `clientNonce`（`api/bots.rs:160-165` 已有早退，不会二次入队）。
- 用户主动重试投递：`attempt+1`、`idempotency_key` 置空，避免与调用方原键混淆。
- 展示性 `@` 的压制不依赖幂等键：它是同一执行内的集合判断。

## 9. 唤醒

四段全部保留，缺一不可。全部指向**房间调度**，不是逐 bot 抢领：

1. 启动时查：投递恢复后，为每个有 `queued` 投递的房间 `ensure_runner`。
2. 转空闲时查：某个成员 turn 结束后，对它名下有 `queued` 投递的所有房间 `ensure_runner`（这是"忙成员被跳过之后谁去叫他"的唯一入口）。
3. 提交后通知：入队事务提交后，对 `room_id` 调一次 `ensure_runner`。
4. 周期补查：复用 `mod.rs:379` 的 300ms `flush_tick`，计数器每 10 次（约 3s）扫一次 `SELECT DISTINCT room_id FROM deliveries WHERE status='queued'`，逐个 `ensure_runner`。

**周期补查是正确性机制，不是优化。** `send_cmd` 失败（启动期 actor 尚未进入 `bots` map，`hub.rs:205-209`）不得把投递标 `failed`，保持 `queued` 等补查。

`ensure_runner` 必须幂等：已有 runner 时只置"队列有变化"，由 runner 在下一步重读，不再 spawn。

## 10. 存储故障与卡片

### 10.1 存储故障

- 完成写入失败：结果留在内存（`pending_completion`），actor 进入"存储故障"状态，**暂停领取**，不宣布完成，不丢结果。
- 重试节奏：**每 3 秒一次，最多 5 次**（约 15 秒）。沿用 `retry_routine_completion` 的形态，固定间隔即可，不做退避算法。
- 超过 5 次 → 保留结果、继续暂停该 actor 的领取，等待手动恢复。
- 其他 bot 不受影响，暂停是 per-actor 的。

**状态的生命周期要覆盖断线**，只广播一次会被重连的客户端错过：

1. 故障状态存在**内存**里（runtime 上的 `storageError`），不依赖数据库。
2. 状态变化时发一次不碰数据库的事件（见下）。
3. 客户端连上时，bot 的运行时快照里带上该字段——重连自然恢复，不需要补发事件。快照要读库；如果连读都失败，说明连接本身已不可用，这一条不适用，不额外承诺。
4. 保存成功后清除该状态，并发一次清除事件。
5. **"重试保存"不依赖卡片存在**：它是 host 的一个方法（`retryDeliverySave { botId }`），客户端从 bot 的状态条调用即可。卡片要等存储恢复后才补写，不能把入口放在一个写不出来的东西上。

**可见性不能走 `emit_bot`。** `emit_bot` 先执行 `store.touch_bot(id)`（`hub.rs:347`，一条 `UPDATE bots SET rev`），存储不可写时它直接返回，事件根本不会发出——最需要报错的时候恰好静默。改用不碰数据库的事件：

```text
{"type":"deliveryStorageError","botId":"…","status":"error","activity":"存储不可写：结果已保留，等待重试"}
```

走现有 events 通道，客户端按 bot 状态展示。

**边界必须写进文案**：若存储持续不可写、随后进程崩溃，未落盘的结果无法保证；恢复时标为"执行结果不确定"，不自动重跑。

### 10.2 卡片

- 按**来源事件 + attempt** 聚合一张卡，目标是卡内的一行：`{ deliveryId, targetBotId, status, detail }`。
- 同一 attempt 原地更新（`set_entry`，rev 递增）；重试创建 `attempt+1` 的新卡，关联原卡，不覆盖旧结果。
- 卡片默认仅一行中文状态，详情折叠；展开仅显示目标当前名字、中文状态、原因、投递次数与重试入口，不重复来源消息正文。三轮保护停止使用明确说明；混合状态保留各状态数量，不能误报全部停止。终端复用选中通知后的 `o` 键展开/收起。
- 失败与中断提供手动重试；重试生成新投递（`parent_id` 指向原投递），旧记录保留。

## 13. 验收

### 13.1 交互

上下键循环、Enter/Tab、Esc、重复键、鼠标悬停与高亮同步；IME 组合期间不误确认；`Shift+Enter` 换行；光标中间插入保留尾文；同名区分；emoji 与中文紧邻。

### 13.2 身份与路由

四端 UTF-16 区间一致；裁剪换算；代理对边界；草稿/离线/重试/历史都带 `mentions`；结构化与手打混用；`@all`；引用；无匹配当文本；歧义拒绝；围栏/行内代码/引用/邮箱/URL 不触发；旧客户端消息入库解析固定。

### 13.3 调度与投递

- 顺序：三人房间，A 提到 B，B 在 A 之后开始且看得到 A 的回复。
- 单 runner：两条消息快速连发，只有一个 runner，不出现两次推进同一投递。
- **领取权**：actor 没有收到 runner 指定的 id 时不得领取；构造"actor 空闲但 runner 尚未轮到"的时序，不得抢跑。同一投递被两处同时指定，条件更新只有一处成功。
- **`room_seq` 排序**：入队顺序与 UUID 顺序不一致时，执行顺序仍按入队顺序。
- 忙成员：A 在别处忙，房间继续；A 空闲后执行，`deferred` 不改变投递身份与 `room_seq`。
- 超时：等待位到期后下一人执行；原投递仍 `started`；迟到结果完成它；已取消时只写迟到记录。
- **`speak` 原文**：用户发一条长消息后立刻补发 30 条，忙成员执行时仍能看到那条消息的完整正文、附件与引用；24 行窗口里没有它也不影响。来源 entry 不可读时投递 `failed`，不得用窗口内容替代。
- 两个独立任务到同一忙成员都保留；两次工具派工到同一目标都保留；工具与文字 @ 不重复派发。
- **`task` 也占等待位**：一条长任务在进行时，房间不开始下一位；超过 10 分钟才继续调度，原执行不被中断。不得出现"任务并行、发言串行"的混合模式。
- **预算预占**：制造 10 个并发超时的 `speak`，在其全部完成前不得再启动第 11 条；`(pass)` 与失败要释放预占；重启 runner 后计数不回退到 0。
- **轮次与深度分开**：连续三轮文字引用在第 4 轮停止；连续 8 次工具派工触发链接上限；两种混合时深度连续累加，不因"文字转工具"或"工具转文字"重置。轮次不因工具调用而减少。
- **派工容量**：同一发送者第 17 个未完成 `task` 被拒绝；全局 64 个未完成时被拒绝；完成后容量释放。深度上限触发时不得把原因写成容量不足。
- **幂等键**：同键同正文返回原 `requestId`；同键不同正文返回冲突错误且不返回原任务结果；不同来源成员/不同群使用相同键互不影响。
- 超过 24 条历史仍不漏单；新消息不撤销已接受任务。
- `/new` 默认等待；强制切换按"先落盘中断、再 `forget_session()`"的顺序；落盘失败时不新建会话。
- 重试：`attempt` 递增，不撞唯一约束；同一幂等键重传返回原投递；用户主动重试不复用原键。

**事务顺序（三条作为验收断言，不是建议）：**

- **幂等先于容量**：先把容量占满（全局 64 或单发送者 16），再用原键重传一个已接受的请求 → 返回原 `requestId` 与当前状态，不报容量错误。
- **并发重传**：两个并发请求带同一个键，只有一个插入成功，另一个回读并返回同一 `requestId`，不抛约束冲突。
- **容量原子**：两个房间并发各发 40 个 `task`，落库后 `task` 未完成总数不超过 64；同一发送者并发 20 个，只有 16 个成功。
- **预算原子**：批次已有 9 条 `claimed`/`started`，同时下发两条 `speak`，只有一条领取成功，另一条置 `cancelled` 并显示原因；不出现 11 条。

### 13.4 崩溃与存储

- 在入队、领取、提交 `started`、发送 prompt、完成落库五个点分别强杀子进程（不能用 `drop(Hub)` 替代）。
- 重启后 `queued`/`claimed` 重新排队，`started` 标中断，不自动重跑。
- `expire_pending` 不碰带 `deliveryId` 的卡片；恢复后卡片状态正确。
- 存储写失败：暂停领取、结果留在内存；3 秒 × 5 次后停下等手动；**故障期间客户端能从 `deliveryStorageError` 事件看到状态**（不能只在数据库里留痕）。
- **故障期间断线重连**：重连后仍能看到该状态（运行时快照里带着它），不是只广播一次就消失；保存成功后状态清除，客户端同步消失。
- **"重试保存"不依赖卡片**：卡片此时写不出来，入口挂在 bot 状态上，调用不存在的 entry 不应成为前提。
- 恢复后能落盘并补写卡片；进程随后崩溃 → "执行结果不确定"，不自动重跑，也不宣称完成。
- 唤醒窗口：投递在 actor 转 idle 的间隙提交，仍被领取。

## 15. 修订记录

### 第一轮：按实现视角收紧

1. **领取必须由 runner 指定**（§5.1、§5.3）：actor 不自行挑投递，`room_seq` 排序。旧写法让 actor 按 `ORDER BY id` 自取，会抢跑并破坏房间顺序。
2. **`speak` 的请求正文来自来源 entry**（§1、§6.3）：24 行窗口只是补充，不足以承载"@A 检查这个错误"里的任务内容。
3. **唯一约束必须含 `attempt`**（§5.1）：否则用户重试撞约束；幂等键不带 `attempt`，重传返回原行，用户重试置空。
4. **预算按批次计**（§6.4）：批次 = 一条用户消息。
5. **有界重试的具体界限与可见性**（§10.1）：3 秒 × 5 次，之后手动；状态必须走不碰数据库的事件，因为 `emit_bot` 自己要先写库。

另：`/new` 的步骤顺序（§7.3）明确为"先落盘中断、再 `forget_session()`"，避免落盘失败时出现会话已切换、旧投递状态不明的组合。

### 第二轮：撤回两处越界判断

1. **`task` 也等待**（§6.2）。上一稿写"`task` 交接后继续"，等于本期新增并行扇出，与既定范围冲突。改回两种投递共用房间等待位，上限 `MEMBER_TIMEOUT = 10 分钟`；超时后继续调度，原执行保留。
2. **轮次与链深不是一回事**（§6.4）。上一稿把 `MAX_ROUNDS = 3` 直接解释成链深，是行为变更而不是措辞调整。恢复轮次语义：`round` 独立计数，`task` 不推进轮次；链深由 `chain_depth` 单独承担，两者都保留。
3. **`MAX_CHAIN` 退役但功能保留**（§6.4）。退役的是独立常量，不是全链保护；`chain_depth` 从来源投递的行值 +1，文字↔工具转换不得回落到内存默认值 0。

### 第三轮：补齐三处可执行性

1. **预算启动前预占**（§6.4）：只统计 `completed` 会在多个超时并存时突破 10 条；改为 `claimed + started + completed` 计数，`noReply`/`failed`/`cancelled` 释放。`queued` 不计。
2. **派工容量不能由深度替代**（§6.4）：群内 `task` 仍受现有数值约束（全局 64、每发送者 16），但按投递行计数，重启后不归零；终态释放。
3. **存储故障状态要有生命周期**（§10.1）：内存保留、重连可见、保存成功后清除；"重试保存"是 host 方法，不以卡片存在为前提。
4. **幂等键进工具签名**（§4、§8）：`message_bot` 增加可选 `idempotencyKey`，作用域 `(来源成员, 来源群, 目标, key)`；同键不同正文返回冲突，不返回另一项任务的结果。

### 第四轮：事务顺序与容量语义

1. **幂等查询先于容量拒绝**（§5.2）：已受理请求的重传不受当前容量影响；并发撞唯一约束时回读原行返回，不把冲突抛给调用方。
2. **容量检查与插入同事务**（§5.2）：`BEGIN IMMEDIATE`，计数与插入同事务，否则跨房间并发会突破 64/16。
3. **预算检查与 `claimed` 预占同一条条件更新**（§5.3）：runner 的预检只是减少无用下发，真正兜底的是领取语句的 `WHERE`。
4. **更正容量谓词**（§6.4）：上一稿写成 `claimed + started`，那会让排队任务不受限；现有 `reserve_message` 是入队即占用、完成才释放，所以容量按 `queued + claimed + started` 计。发言预算仍不计 `queued`——两个计数器语义不同，不能合并。
